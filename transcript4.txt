1	# Verification Gap Review
2	
3	**Goal:** Find changed behavior that could break without reliable verification catching it. Ask one question — "if the behavior this change is supposed to produce broke where it's actually used, would verification fail?" Do not hunt for correctness bugs, but report genuine problems you notice while tracing verification.
4	
5	The main verification gap shapes are:
6	
7	1. **Regression gap:** the changed code regresses where it's used, and no test covering that use would fail.
8	2. **Missing-adoption gap:** a place that should now use the new behavior doesn't; it handles the same case its own way, or not at all, and no test would flag the omission.
9	3. **Broken-verification gap:** a test appears to cover the changed behavior, but would not actually protect it because it is skipped, flaky, not run in the normal verification path, or too weak to observe the regression.
10

13	- Read a test before claiming what it covers, runs, asserts, or misses.

21	### Step 1: Screen for behavioral change
22

46	
47	A `Missing-adoption gap` qualifies not by the adoption failure alone but by a supersession signal: the change gives clear evidence the new behavior is meant to replace the local one — PR intent, naming or docs, a replaced sibling site, deleted duplicate logic, or a test defining the new rule — and the local site shares the same observable contract. 29	## Technical Decisions
30	
31	- **Stack:** React + Vite, Tailwind CSS (mobile-first), `react-leaflet` + Leaflet with OpenStreetMap standard tiles (keyless, attribution visible), Vitest + React Testing Library. No component library.
32	- **Data loading (readiness decision):** the spec says static import, but loading/error/retry states require a mechanism that can actually fail. Use one that can (e.g. `fetch` from `public/` or a dynamic `import()`) and document the choice in the README.
33	- **Routing (readiness decision):** React Router. `/` is the list, `/parks/:id` is details (supersedes the design's `?park=` option). Unknown id shows "park not found" with a way back. Browser Back must work.
34	- **Data shape:** array of park objects with `id`, `name` (treat as required); `description`, `location.{lat,lng,address}`, `amenities` (kebab-case tokens), `hours` (free text, shown as written), `images` (URL array), `acreage`, `rating` (0–5) may each be missing, null, or empty. function fileStem(pathOrUrl) {
  const withoutQuery = pathOrUrl.split(/[?#]/)[0]

  if (typeof value !== 'string') return null

## Intent

**Problem:** The `/` route shows only an "All parks" heading. A resident cannot browse parks or open one without a map, and the list is the main way to choose a park (CAP-2).

**Approach:** Replace the list placeholder with an "All parks" heading, a one-line hint, and a `<ul>` of 12 park cards, sorted A–Z by the existing loader. Each card is a single React Router `<Link>` to `/parks/:id`. When the user comes back to `/` from a park, focus returns to that park's card.

## Boundaries & Constraints

**Always:** use the normalized parks from `useParks` as they are (order and `number` come from the loader, never recomputed); never invent data; one Tab stop per card; amber `focus-ring` on every card; touch target ≥ 44px; Tailwind tokens from `src/index.css`.

**Never:** details content, the "All parks" back control or focus-to-heading on details (Story 1.3); map or markers (1.4); desktop sidebar/phone toggle layout (1.5); clickable `<div>`s; a nested interactive element inside a card.

export function normalizePark(raw) {
  const park = raw && typeof raw === 'object' ? raw : {}
  const location = park.location && typeof park.location === 'object' ? park.location : {}
  const lat = numberInRange(location.lat, -90, 90)
  const lng = numberInRange(location.lng, -180, 180)
  const acreage = finiteNumber(park.acreage)

  return {
