  Recommended path for a 2-hour build

  The full BMad Method planning path (product brief, then PRD, then UX, then
  architecture, then epics) would use up most of your two hours before any code
  exists. The brief is already a clear requirements document, so use the short
  path:

  Turns the PDF brief, the sample data and your decisions into a short SPEC.md,
  then splits it into epics and stories for you to review. Your decisions to
  feed it: React, Tailwind, Leaflet, a mobile-first layout, and no backend.
  Invoke it with:

  2. [SP] Sprint Planning: bmad-sprint-planning, required before building
  Checks that the plan is ready to build and creates sprint-status.yaml. This
  also clears the first item the BMAD Loop readiness check failed on.

  3. [BD] Build: bmad-build, one story at a time
  You can do this interactively. Or you can let bmad-loop run work through the
  stories unattended, once the git and multiplexer items from that check are
  fixed.

  Optional:
  - [CU] Create UX: bmad-ux. Only worth running once your Claude Design files
    are in design/. Don't wait for them: the epics and stories don't depend on
    the visual design, and the styling story can use design/ when it arrives.
  - [CA] Architecture: bmad-architecture. Skip it. The spec can record your few
    stack decisions.

  On Leaflet

  Leaflet is a good choice here. Use react-leaflet with OpenStreetMap tiles:
  - No API key: the brief says the interviewer must be able to run the app
    without your credentials.
  - No location needed: the map centres on the bounds of the park data, so it
    works without the resident's location.
  - Accessibility: map markers aren't very keyboard-friendly. That's fine
    because the brief makes the list and details view the accessible route. Make
    the list the main keyboard path, and have selecting a park in the list
    highlight it on the map.

  The alternatives are worse fits. Mapbox and Google Maps both need a key, and
  MapLibre adds complexity without much benefit at this size.

  Things from the brief to plan into the stories

  - AI logs: you must submit the full, unedited AI conversation logs, and this
    session counts. Keep these transcripts.
  - README story: the README needs run instructions, what works, what's left

    Make it its own story at the end.
  - Missing data: park fields may be missing or null, and arrays may be empty.
    Make handling these an acceptance criterion on the details and list stories
    rather than leaving it to the end.
